# Pipeline Job Splitting Workflow

## 概述

这个参考文件提供把已有管线改造成细粒度单核 HPC 子任务工作流的详细方法。默认目标不是重写算法，而是把“一个粗粒度大任务”变成“多个可手动批量提交的细粒度子任务”。

## 1. 检查现状

先识别以下内容：

- 项目根目录在哪里。
- 哪个脚本是真正的主 runner。
- 当前配置文件在哪。
- 当前任务列表是否已经存在，例如 `list.txt`、`samples.tsv`、`regions.txt`。
- 当前调度脚本是否把业务逻辑直接写进 `.lsf`，还是只是包装主 runner。

优先读取：

- `pipe/`
- `script/`
- `conf/`
- `python/`
- `src/`

如果已经存在清晰的主 runner，则尽量围绕它改造，不要再创建第二套执行逻辑。

## 2. 确定切分维度

优先使用已经存在的任务清单作为切分轴。常见切分维度包括：

- 样本列表的每一行
- 染色体列表
- 区域列表
- contig 列表
- 任务参数矩阵

默认优先级：

1. 现成的任务列表
2. 现成的输入目录清单
3. 可显式枚举的区块清单
4. 最后才考虑改写模块内部循环

如果一个任务本质上是 embarrassingly parallel，优先做任务切分，不要继续让单个脚本内部持有大量并行核数。

## 3. 改造主 runner 的最小接口

主 runner 最好支持“外部注入任务配置”。推荐形式：

```bash
bash script/run_pipeline.sh /path/to/task.conf
```

如果当前 runner 只会读取固定配置文件，优先做最小改造：

- 允许第一个命令行参数覆盖默认 `CONF_FILE`
- 若未传参，再回退到原默认配置

目标是让批次生成器只需要为每个子任务写一个子配置文件，而不需要复制整套业务逻辑。

## 4. 设计批次生成脚本

在 `pipe/` 下新增一个总控生成脚本。它应当负责：

1. 读取基准配置文件。
2. 解析任务列表路径。
3. 清洗任务列表，去掉空行和注释行。
4. 显式检查坏格式记录。
5. 按固定粒度切分任务列表。
6. 为每个子列表生成唯一子配置。
7. 为每个子配置生成唯一调度包装脚本。
8. 写出批次目录说明和手动提交说明。

生成脚本默认只做“生成”，不做“提交”。

## 5. 设计批次目录结构

默认推荐：

```text
conf/hpc_batches/<batch_id>/
- split/
- conf/
- lsf/
- logs/
- README.submit.txt
```

其中：

- `split/`：切分后的任务列表
- `conf/`：每个子任务的配置文件
- `lsf/`：每个子任务的 LSF 包装脚本
- `logs/`：LSF 输出日志目标目录
- `README.submit.txt`：手动提交说明

如果项目目录所在磁盘空间紧张，允许把整个 `batch_root` 改到项目外的大磁盘，例如 `/data/...`。

## 6. 项目内批次目录与项目外批次目录的选择

优先考虑以下规则：

- 如果项目目录空间充足，批次目录放在项目内，路径更直观。
- 如果项目目录经常出现 `No space left on device` 或 inode 紧张，把批次目录放到其他磁盘。
- 如果批次目录在项目外，调度包装脚本中不得用相对路径猜项目根目录。

一旦批次目录不在项目内，wrapper 中必须写明：

- 绝对 `PIPELINE_ROOT`
- 绝对 `CONF_FILE`
- 绝对主 runner 路径

## 7. 设计子配置文件

每个子配置默认由“基准配置 + 少量覆盖”组成。优先只覆盖：

- `LIST_PATH` 或等价任务列表变量
- `JOBS=1` 或等价并行参数

不要轻易在子配置中重写大量业务参数，除非任务切分本身要求变化。

推荐策略：

- 保留基准配置中的软件路径、参考文件路径、输出根目录
- 只修改子任务输入和子任务资源规格

## 8. 设计调度包装脚本

调度包装脚本应尽量轻量。它的职责通常只有：

1. 声明资源
2. 计算或写入固定路径
3. 调用主 runner

默认不要把分析逻辑直接写进 `.lsf`。

LSF 默认策略：

- 每个任务 `#BSUB -n 1`
- 默认 `span[hosts=1]`
- 默认由用户手动 `bsub < xxx.lsf`

## 9. 处理磁盘空间与 inode 问题

如果远程服务器报：

- `No space left on device`
- `couldn't open temporary file`

优先考虑：

- 目标分区磁盘空间满
- 目标分区 inode 用尽
- 生成脚本使用了 `sed -i` 一类需要额外临时文件的写法

推荐处理方式：

- 先检查 `df -h`
- 再检查 `df -i`
- 生成批次文件时尽量直接写目标文件，减少额外临时文件
- 必要时把批次目录迁移到更大的磁盘挂载点

## 10. 最终验证流程

至少检查以下内容：

- 生成脚本本身语法正确
- 任意一个生成出的调度脚本语法正确
- 子配置文件数量等于切分后任务列表数量
- 调度脚本数量等于子配置数量
- 每个子任务资源规格符合预期，默认应为 1 核
- 每个子配置都指向唯一任务列表
- 手动提交说明完整且路径正确

如果上述检查不通过，不要直接交付。
